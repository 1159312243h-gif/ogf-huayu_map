# 华域地图渲染与三维建模实施方案

文档状态：实施中
整理日期：2026-09-25
最后修订：2026-09-28
适用基线：华域地图 5.0

## 1. 目的

本方案整理华域地图后续渲染与三维建模工作的实施顺序、技术边界和验收要求。工作按“先修补现有问题，再开展隔离实验，最后决定是否产品化”的顺序推进。

近期重点是稳定现有华域标准和华域深夜视图；中期重点是小比例尺城乡表达、道路层级和山峰标注；长期再建设独立建成区数据、程序化三维建筑、精细地标与 OGF 专用地形。

## 2. 已确认的技术基线

### 2.1 数据与渲染关系

华域标准和华域深夜采用分级混合数据管线。较远比例尺继续由 MapLibre 读取 OGF OpenMapTiles 矢量瓦片；约 500 米及更近时，当前 OGF 固定分片完整到达后，华域自有实时层成为常规地表、水体、道路和铁路的主数据源。

当前结构分为三层：

1. OGF 基础矢量数据：负责较远比例尺，并作为近景实时数据加载中或失败时的即时回退；官方 Vector 仍包含自己的建筑瓦片。
2. 华域稳定快照底图：固定 `z13-z14` 网格按需生成并保留三小时；过期快照先返回、后台刷新，完整视口就绪后接管对应常规矢量层。
3. 华域近景实时明细：`z15` 网格在边缘按两分钟周期读取当前 OGF；父级快照先显示，完整明细视口就绪后一次性接管。已完整加载到浏览器的当前视图稳定保留三小时，避免停留期间反复重绘。
4. 华域渲染样式：颜色、字号、道路宽度、图层顺序和基础建筑材质。
5. 华域动态覆盖层：当前 OGF 建筑分片、行政区补充标注、体育、花园、城墙、普通墙体、栅栏、城门和空中绿地等专门内容。

华域视图与官方 Vector 使用相同的 OGF 数据体系，但加载不同的样式文件。修改华域标准或华域深夜不会改变 OGF 官方样式，也不会影响图层列表中的官方 Vector。

### 2.2 当前更新方式

| 内容 | 当前更新方式 |
| --- | --- |
| 较远比例尺的 OGF 道路、水体、土地利用和地名 | 等待 OGF 重新生成矢量瓦片并刷新缓存 |
| 约 500 米及更近的常规地表、水体、道路和铁路 | `z13-z14` 按需生成三小时稳定快照；`z15` 边缘明细两分钟更新，浏览器完整视图稳定保留三小时并原子接管 |
| 华域建筑高度和基础三维建筑 | `z11-z15` 网格按需读取当前 OGF Overpass；近景使用 `z15` 小分片，边缘和浏览器稳定缓存三小时 |
| 官方 Vector 建筑 | 保持原有 OGF 矢量瓦片更新周期，不受华域建筑实验影响 |
| 城墙、墙体、栅栏、城门、空中绿地 | 页面按视图从 OGF Overpass 查询并生成 |
| 华域颜色、字号、图层顺序 | 修改华域样式并重新部署 |
| 已打开且停留不动的页面 | 不接收持续推送，通常需要刷新或重新进入区域 |

因此，现有机制是“稳定快照兜底、近景明细按需更新”，不属于严格的实时推送，也不是已经预生成全球全部瓦片。首次访问从未缓存的区域仍需要等待 OGF；该区域形成快照后，后续访问和三小时刷新不再阻塞于上游更新。

## 3. 实施原则

- 以 4.0 为稳定基线，补丁和实验分开提交。
- 未经明确允许，不修改导航系统及其数据和算法。
- 官方 Vector 始终保留原样，不承载华域实验逻辑。
- 实验功能先作为本地或可选视图存在，不直接替换正式效果。
- 一次只处理一个已确认问题，避免跨模块连带修改。
- 每个阶段先完成本地验证，再决定是否上传 Cloudflare。
- 林地表示地表植被，山体表示地形，两者不互相推断。
- OGF 原始数据、华域样式、自建数据层和精细三维模型独立维护。
- 数据不足时不伪造精度；推测高度和推测模型必须与实测或标注数据区分。

### 3.1 强制存档规则

- 每次开始修改前，先将整个 `outputs/ogf-atlas` 保存为独立完整基线包。
- 每次形成可查看的迭代后，再保存一个独立完整结果包；不能只保存本次改动的几个文件。
- 归档目录使用唯一版本名，禁止覆盖、复用或原地更新旧版本。
- 每个完整包必须包含逐文件 `SHA256.txt`、版本用途和对应版本索引记录。
- 归档后比较运行目录与归档目录的文件数量和哈希，只有完全一致才视为存档成功。
- 回退前先保存当前完整状态；回退后再次生成完整包并验证浏览器效果。
- 本地存档、Cloudflare 部署和 OGF 数据更新是三件独立事项，部署不能代替存档。

## 4. 总体实施顺序

```text
现有问题补丁
    ↓
视觉回归与性能基线
    ↓
小比例尺城乡效果实验
    ↓
道路层级与山峰标注
    ↓
评估是否需要独立 built_up 数据
    ↓
基于完整 OGF 道路的桥梁高度渲染
    ↓
自有程序化三维建筑
    ↓
精细地标模型
    ↓
具备可信高程数据后建设真实地形
```

后续工作首先只进入第一阶段，不同时展开建成区、三维建筑或地形实验。

## 5. 第一阶段：现有问题补丁

### 5.1 目标

暂停增加大型功能，先稳定当前华域标准、华域深夜及其动态覆盖层，建立可重复验证的视觉和性能基线。

### 5.2 检查范围

- 华域标准与华域深夜的图层结构和功能一致性。
- 俯视与倾斜视角切换时的图层显隐。
- 建筑、城墙、普通墙、城门和空中绿地的遮挡顺序。
- 城墙和城门闪烁、重叠、凹陷、高度异常及边缘多余图形。
- 土地利用与自然覆盖层的上下关系。
- 高速、干线和普通道路的层级差异。
- 国家、省道级、城市、区县、街道、镇、社区和村庄的文字层级。
- 不同缩放级别下标签突然消失、相互覆盖或密度异常。
- 华域标准、华域深夜和官方 Vector 切换后是否残留动态覆盖层。
- 地图平移、缩放和倾斜时的帧率、请求数量与内存增长。

### 5.3 补丁规则

- 每个补丁只对应一个已复现问题。
- 不借补丁机会重构搜索、导航或交通数据。
- 每个问题至少验证标准、深夜、俯视、倾斜四种状态。
- 典型大城市、普通城市和低密度区域分别回归。
- 修复前后保留相同位置、缩放和视角的截图。
- 未经确认不上传生产环境。

### 5.4 完成条件

- 已知渲染问题有明确复现步骤和修复记录。
- 视图切换不残留图层或事件监听。
- 连续缩放、倾斜和旋转不出现明显闪烁。
- 当前导航、搜索和交通展示回归无变化。
- 建立后续实验可复用的截图点位和性能记录。

## 6. 第二阶段：小比例尺城乡效果实验

### 6.1 目标

在较小比例尺下形成“建成区白色、非建成区绿色”的清晰城乡结构，同时保留水体、行政区、道路和重要地名。

第一版只修改实验样式，不建立新数据管线。

### 6.2 建议图层顺序

```text
清淡绿色陆地底色
水体
白色建成区蒙版
林地 / 农田 / 草地 / 公园
道路与铁路
行政边界
国家、省道级地名、城市名和山峰
```

自然覆盖继续位于白色建成区之上，使城市公园、农田、林地和草坪仍能正确显示为绿色。

### 6.3 第一版建成区来源

使用现有 `landuse` 中的以下类型生成白色或浅灰白色蒙版：

- `residential`
- `commercial`
- `retail`
- `industrial`

校园、铁路用地、港区、机场和机构用地是否并入建成区，应通过代表区域视觉测试决定，不在第一版中直接扩大规则。

### 6.4 缩放策略

| 缩放级别 | 主要内容 |
| --- | --- |
| `z5-z7` | 高速和主要干线、国家与高等级行政区、主要城市和主要山峰 |
| `z7-z9` | 逐步加入一级道路、省级名称和更多建成区 |
| `z9-z11` | 加入次一级道路，并向当前详细土地利用配色过渡 |
| `z11+` | 恢复学校、商业区、零售区等现有详细分类效果 |

过渡应使用连续缩放表达式，避免在某一级缩放突然变色或消失。

### 6.5 验收重点

- 城市轮廓是否比现状更容易识别。
- 未绘制土地利用的城镇是否出现明显绿色空缺。
- 港区、校园、工业区和交通设施是否被错误处理。
- 城市公园和自然覆盖是否仍然清晰。
- 道路是否压过行政区和城乡结构。
- 从小比例尺放大到城市级别时是否平滑过渡。

## 7. 第三阶段：道路层级与山峰标注

### 7.1 道路层级

- `z5-z7` 只保留高速和主要干线。
- `z7-z9` 再加入一级道路。
- 更高缩放级别逐步加入次干路和普通道路。
- 降低低缩放高速与干线的饱和度和描边强度。
- 保持高速、干线和普通道路的宽度与颜色差异。
- 大比例尺继续保留当前详细道路表达。

### 7.2 山峰标注

OGF 当前矢量瓦片提供 `mountain_peak`，包含名称、海拔 `ele` 和重要性 `rank`。近期可以：

- 显示重要山峰名称与海拔。
- 使用 `rank` 和缩放级别控制显示密度。
- 低缩放只显示代表性山峰。
- 避免山峰名称与行政区、城市名争夺同一位置。

山峰是点状地貌信息，不用于推断山体范围。林地也不增加伪山体阴影或伪等高线。

## 8. 第四阶段：独立建成区数据层

### 8.1 启动条件

仅当第二阶段纯样式方案在代表性区域出现大量缺口，且缺口不能通过合理的现有 `landuse` 规则解决时，才建设独立 `built_up` 数据层。

### 8.2 数据来源

概化建成区可以综合：

- 住宅、商业、零售和工业土地利用多边形。
- 建筑密度。
- 道路密度。
- 交通设施和连续硬化区域。
- 必要的孔洞清理、边界平滑和多级概化。

### 8.3 输出与维护

输出为独立矢量瓦片或 PMTiles，不替换 OGF 原始数据。不同缩放级别使用不同概化精度，并保留数据版本与生成时间。

```text
OGF 数据变化
    ↓
每日增量提取
    ↓
生成 built_up
    ↓
自动质量检查
    ↓
原子发布新版本
    ↓
异常时继续使用上一稳定版本
```

### 8.4 质量要求

- 不把孤立道路缓冲区误判为城市。
- 不填平大型湖泊、河流、公园和农田。
- 低密度村庄与连续城市建成区使用不同阈值。
- 数据不完整时允许保守缺失，不允许大面积错误留白。

## 9. 第五阶段：桥梁高度渲染

### 9.1 状态与边界

此前的客户端桥梁网格试验已经全部从运行目录撤销，当前地图保持 Cloudflare Pages 发布版效果。本阶段只保留方案，不在处理其他渲染问题时重新启用桥梁代码。

第一版桥梁只实现固定高度路面和接口引坡，不实现拱桥、悬索、桥墩、阴影或装饰结构。导航、道路拓扑、官方 Vector 和 OGF 原始数据均不修改。

### 9.2 数据与连接关系

- 使用 OGF 完整道路 way 及其完整节点序列，以 OGF way ID 去重。
- 只通过精确共享的 OGF node ID 判断道路连接，不按经纬度距离猜测连接。
- 不使用被矢量瓦片边界裁开的线段重建道路，不跨瓦片补带或吸附端点。
- 矢量瓦片继续负责现有二维道路底图；桥梁高度层只读取完整 OGF 几何并覆盖对应道路。
- 主路、匝道、步行桥和铁路分别保留各自原有宽度，不因同属一个桥梁组而统一宽度。

### 9.3 高度剖面

第一版只依据 `layer` 形成明确的分段线性剖面：

```text
layer <= 0：不生成自定义高架桥面
layer = 1：路面高度约 4.5 m
layer > 1：4.5 m + (layer - 1) * 3.5 m
```

- 同一 `layer` 的整段道路保持一个固定高度，所有中间节点均为水平面。
- 同层道路在共享节点处直接连续，不生成坡度或额外连接片。
- 桥梁接普通道路时，从共享节点沿相邻普通道路向外取得真实道路几何作为引坡。
- 不同 `layer` 在共享节点相接时，只在该接口前后设置一次引坡。
- 引坡沿道路累计里程做线性插值，不使用会产生波浪的 smoothstep 曲线。
- 坡长按高度差和约 5% 目标坡度计算；当前 way 不够长时继续沿精确连接的相邻 way 延伸，不凭空补线。
- 若缺少可确认的相邻道路或长度仍不足，该端点保持二维发布版效果并记录为数据不足，不生成陡坡。

### 9.4 渲染结构

当前 MapLibre 版本不支持可直接用于道路的 `line-z-offset`，因此高度层需要一个最小的连续路面网格，但其职责仅限于按完整道路中心线生成左右边界和逐节点高度：

- 每条精确连接的道路走廊生成一条连续桥面，不按瓦片或固定距离切块。
- 桥面颜色、外轮廓和宽度继承华域现有道路等级样式。
- 路面下方使用统一约 0.35 m 的结构厚度，只生成纵向侧面。
- 不生成横向封口、阴影带、跨道路连接片或邻近道路之间的填充面。
- 只有引坡区的节点高度变化，其余节点高度完全相同。
- 标准与深夜视图共用同一几何，只替换材质颜色。

### 9.5 验收条件

- 俯视时桥面宽度连续，不出现鼓包、尖刺、锯齿或糊边。
- 倾斜和旋转时，同一 `layer` 全程保持水平直面。
- 高度只在已确认的层级接口前后线性变化一次。
- 匝道始终明显窄于主路，平行道路不会互相连接。
- 平移跨越瓦片边界时几何不改变、不闪烁且不重复绘制。
- 桥梁层关闭或数据失败时完整回退到当前发布版道路。

## 10. 第六阶段：自有程序化三维建筑

### 10.1 当前基础与目标

当前华域标准和华域深夜使用 v10 分片模型：当前 OGF Overpass 建筑按 `z11-z15` 地理网格读取，并通过华域自己的 GeoJSON `fill-extrusion` 生成基础体块。约 500 米使用 `z14`、约 300 米使用 `z15`，全部级别稳定缓存三小时；较细分片避免密集城区单片数据量过大。客户端最多并发 3 个分片、保留最近 72 个分片，中心分片先到先显示；发布建筑在完整覆盖前为缺失区域兜底。

普通建筑继续以 OGF 建筑轮廓为基础，不手工建模全国建筑。v4 已能做到任意区域按需加载，但这只是“全域可寻址”，不是已经预生成全国数据；冷分片仍要等待第一次 Overpass 查询。生产级目标仍是每日生成自建 MVT/PMTiles，页面端保留当前分片接口作为短期实时方案和失败回退。

### 10.2 属性优先级

优先支持：

- `height`
- `building:levels`
- `min_height`
- `building:part`
- `roof:shape`
- `roof:height`
- `building:material`
- `building:colour`
- `roof:material`
- `roof:colour`

高度按以下优先级计算：

1. 完整 OGF 数据中的 `height` / `min_height`。
2. `building:levels * 3 m` 与 `building:min_level * 3 m`。
3. 按建筑类型使用克制的默认高度；当前基础体块回退为 3.2 米。
4. 后续屋顶阶段再叠加明确的 `roof:height`，不得提前猜测复杂屋顶。

推测高度必须写入内部 `heightSource=estimated` 标记，与 OGF 明确标注值分开；界面不把推测高度表述为真实数据。

### 10.3 分阶段实现

#### A. 华域基础建筑体块

- 当前 v4 使用固定 `z14` 数据网格按需请求，不发送全国范围或无限扩张的 Overpass 视窗查询。
- 已接管日夜配色、高度回退、透明度和缩放策略；Vector 的三层建筑只在华域视图中关闭，官方 Vector 保持原样。
- 使用 OGF `min_height` 或 `building:min_level` 正确表现架空层、连廊和悬挑部分。
- 后续再按住宅、商业、零售、工业、学校、医院、交通、宗教和公共建筑设置克制的独立色相。

#### B. 建筑分段与程序化屋顶

- 仅在 `z17+` 和有限视图范围读取需要补充的完整 OGF 建筑关系与 way。
- 有 `building:part` 时优先绘制分段，避免父建筑轮廓与分段重复拉伸。
- 第一批屋顶支持 `flat`、`gabled`、`hipped`、`pyramidal` 和 `dome`。
- 普通体块继续使用 MapLibre `fill-extrusion`；屋顶和复杂分段使用独立 Three.js/自定义三维层。
- 无可靠屋顶方向、层数或高度时回退到平顶体块，不猜测复杂造型。

#### C. 精细地标

- 少量车站、机场、体育场、塔楼、宫殿和城门使用独立 `GLB/glTF` 模型。
- 精细模型通过 OGF 对象 ID 绑定，不与普通程序化体块同时绘制。
- 模型不可用时自动回退到程序化建筑。

### 10.4 图层关系

```text
地表与土地利用
普通道路和铁路
基础建筑体块
building:part 与程序化屋顶
桥梁、架空连廊和空中绿地
少量精细地标模型
道路与 POI 注记
```

城墙、城门、墙体和栅栏继续由各自图层负责，不合并进普通建筑引擎。建筑、空中绿地和未来桥梁必须使用统一高度基准，避免互相穿插。

### 10.5 细节层级

| 缩放与视角 | 三维内容 |
| --- | --- |
| 较远视角 | 二维建筑块或概化城市轮廓 |
| `z15` | 简单建筑拉伸 |
| `z16-z17` | 高度、层数和架空部分 |
| `z17+` | 屋顶、建筑分段和墙体细节 |
| 倾斜视角 | 按距离启用完整三维 |
| 俯视视角 | 优先保持轻量二维表达 |

### 10.6 更新与性能要求

- 只加载当前视图及有限缓冲区内的三维数据。
- 按缩放级别和屏幕尺寸控制细节。
- 避免同一对象同时由基础建筑层和动态覆盖层重复拉伸。
- 对城墙、城门和建筑交界处进行深度冲突检查。
- 不发送全国范围的实时 Overpass 查询；短期只查询可见固定网格，长期由每日 MVT/PMTiles 承担主三维数据加载。
- 普通体块按固定分片读取当前 OGF 数据；浏览器与边缘稳定缓存三小时，同一完整视图不在使用过程中周期性重建。
- 屋顶和精细模型设置数量、距离和显存预算，超出预算时优先回退到基础体块。
- 正式启用前分别记录平面、倾斜、旋转时的首屏时间、帧率、内存和请求数量。

## 11. 第七阶段：精细地标模型

### 11.1 适用对象

少量高辨识度建筑可以人工制作 `GLB/glTF` 模型，例如：

- 机场航站楼。
- 火车站。
- 体育场和大型场馆。
- 电视塔和城市塔楼。
- 宫殿、城门、寺庙和代表性建筑。

### 11.2 接入方式

使用 Three.js 自定义图层叠加到 MapLibre，通过 OGF 对象 ID、经纬度、旋转角和基准高度进行锚定。

精细模型作为独立覆盖层存在：

- 不修改官方 Vector。
- 按距离和缩放级别加载。
- 支持单独关闭。
- 模型不可用时回退到程序化建筑。
- 不一次性加载整座城市的高精度资源。

### 11.3 更新边界

精细模型需要人工维护，不会仅凭 OGF 二维轮廓自动重建。模型的锚点、显隐状态和绑定对象可以随 OGF 数据更新。

## 12. 第八阶段：真实山体与地形

### 12.1 当前能力与限制

当前 OGF 矢量瓦片有山峰点，但没有：

- 等高线。
- 山脊和山谷。
- 坡度。
- 连续高程栅格。
- `hillshade`。
- Terrain DEM。

林地是土地覆盖，山体是地形。平原可以有森林，山地也可以由草地、裸岩、农田或建成区覆盖。因此不能从林地边界推断山体。

现实世界的 SRTM、Mapbox DEM 等也不能用于 OGF 虚构地理。

### 12.2 无 DEM 时的策略

- 只显示可信山峰名称和海拔。
- 不制作看似真实但没有数据依据的阴影。
- 不从山峰点插值并对外宣称为真实地形。
- 不将林地渲染成山体。

### 12.3 未来地形管线

只有取得或建立可信的 OGF 专用高程数据后，才实施：

1. 清洗高程点、山脊、水系和海岸约束。
2. 生成连续 DEM。
3. 转换为 Terrain-RGB 或 Terrarium 瓦片。
4. 生成 hillshade 和等高线。
5. 在地形上覆盖林地、草地、裸岩、农田和建成区。
6. 验证道路、水体、桥梁、建筑和城墙是否贴合地表。

地形数据必须单独版本化，并允许在性能不足或数据异常时关闭。

## 13. 后续自动更新架构

| 内容 | 建议更新方式 |
| --- | --- |
| OGF 基础矢量 | 继续负责较远比例尺，并作为近景加载中和失败时的回退 |
| 华域近景自主底图 | 现阶段以固定网格 Overpass 分片为主；后续评估每日 MVT/PMTiles，减少冷分片延迟和上游压力 |
| 华域标准与深夜样式 | 代码审查后随网站版本部署 |
| 动态行政区、墙体和空中绿地 | Overpass 按视图加载，增加合理缓存与失败回退 |
| 自建 `built_up` | 每日增量构建并原子发布 |
| 桥梁高度层 | 读取完整 OGF way 与共享 node；缓存按 OGF 对象 ID 失效 |
| 程序化三维建筑 | 短期固定网格按需读取并边缘缓存；长期与每日自建 MVT/PMTiles 同步增量构建 |
| 精细地标模型 | 人工维护，独立清单和版本 |
| 未来 DEM | 独立构建、独立版本、独立回退 |

任何自动任务都必须保留上一稳定版本。构建失败、数据量异常或质量检查不通过时，不得覆盖线上数据。

## 14. 验证矩阵

每项渲染改动至少覆盖以下组合：

### 14.1 视图

- 华域标准。
- 华域深夜。
- 官方 Vector 对照。

### 14.2 摄像机

- 俯视。
- 典型倾斜视角。
- 旋转后的倾斜视角。

### 14.3 比例尺

- 国家与大区级。
- 200 km 与 100 km 附近。
- 城市级。
- 街区级。
- 建筑级。

### 14.4 区域类型

- 高密度大城市。
- 普通城市。
- 城郊结合部。
- 农田与林地区域。
- 山峰较多区域。
- 城墙、城门和精细建筑区域。

### 14.5 回归内容

- 标签优先级和遮挡。
- 图层顺序和颜色。
- 数据缺失与失败回退。
- 初次加载和二次加载速度。
- 平移、缩放、倾斜与旋转流畅度。
- 桌面与移动视口。
- 搜索、交通展示和导航无意外变化。

## 15. 阶段准入与发布门槛

每个阶段进入下一阶段前必须满足：

- 当前阶段问题已形成可复现清单。
- 修改范围与非目标功能明确。
- 自动检查和人工截图回归通过。
- 官方 Vector 未受影响。
- 页面性能没有不可接受的退化。
- 数据失败时存在回退方案。
- 用户确认实验效果可以继续。
- 用户确认后才上传 Cloudflare。

## 16. 下一步

桥梁仍只保留本方案、不进入运行代码。自有建筑已替换华域标准与华域深夜的基础建筑层；约 500 米及更近的常规底图也已在完整视口就绪后使用当前 OGF 分片作为主源，并保留发布版矢量即时回退。下一步观察冷分片响应时间、快速连续平移、密集城区帧率和 Overpass 负载，再决定是否建设每日 MVT/PMTiles，使全国任意地点首次访问也能稳定快速显示，并逐步将标签与更多专用要素迁移到自主数据管线。
