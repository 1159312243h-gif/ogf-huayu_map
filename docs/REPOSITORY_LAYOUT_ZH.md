根目录部分旧文件仍被一次性修复工作流引用。整理时先核对引用，不直接移动或删除这些文件。仓库目录重排不会自动改变网页内部模块结构，也不应顺带修改渲染、导航、账号或刷新行为。

## 本次已做的非破坏性调整

- 新增 `/releases/` 忽略规则，防止下一次 `git add .` 又加入新的一整份网站；Git 已跟踪的 50 份历史包仍在，不会被该规则移除。
- 更新 README 的目录入口和已发布构建说明，运维手册区分本地存档与 GitHub Releases 上传。
- 不改生产文件、更新工作流或源数据，不删除历史包，不重写提交，不执行强制推送或本机临时文件清理。

这一步防止新增整包继续进入 Git，不会立即消除已有约 3.5 GB 历史，也不能停止当前生成数据的历史增长。

## 后续迁移的具体顺序

1. **先保存可恢复备份。** 记录当前提交、分支和发布版本；完整保存 Git 历史，逐版本核对已有发布包的 SHA-256。未跟踪或被忽略的必要文件另行备份，不能假定 Git 备份包含它们。
2. **迁移版本整包。** 每个版本生成 ZIP、独立 SHA-256 和版本索引，上传 GitHub Releases 后下载复核。至少选一个旧版本实际恢复并完成现有校验，确认回退方式可用后再讨论移出主分支。Release 附件虽然不进入源码对象库，仍需保管，不能当作不会丢失的唯一备份。
3. **减少日常检出负担。** 可让校验、部署及自动更新任务仅检出所需目录，跳过历史 `releases/` 副本；保留修复工作流需要的根文件。先在独立检出中执行现有校验，再调整正式流程。这样可减少传输和展开量，但不会让服务器端 Git 历史变小。
4. **再处理生成数据增长。** 可将完整数据代发布为独立资产，由部署流程下载、核对清单和代际后组装到现有 `site/` 路径；主库保留代码、人工规则及小型数据版本索引。三小时重建、两分钟模型检查、五分钟新代检查保持原样。必须先验证完整包、失败保旧、离线兜底及旧版回退，不能直接从当前生产包删掉快照。个人账号、收藏和贴图仍留在 D1，不进入公开资产。
5. **最后才真正缩小历史库。** 全部备份、迁移及回退验证完成后，在隔离副本准备历史改写或建立精简的新主库，测量最终大小并列出旧提交／分支受影响范围。历史改写可能需要强制更新远端或切换仓库及工作流，必须另外取得明确授权后执行。单纯删当前目录、增加 `.gitignore` 或改用 ZIP，都不会移除旧 Git 对象；GitHub 的最终空间回收还取决于其保留与清理状态。

本次没有实施上述历史迁移，没有上传 Release 附件，也没有改变 Cloudflare 部署。
